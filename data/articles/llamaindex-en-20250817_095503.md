# LlamaIndex: A Practical Guide to Building Retrieval-Augmented LLM Applications

## 1. What is LlamaIndex? A concise overview

### Purpose: data orchestration & RAG — goals and typical workflows
LlamaIndex (formerly GPT Index) is an open‑source data orchestration framework whose primary goal is to make Retrieval‑Augmented Generation (RAG) and document‑centric LLM apps easy to build. It supplies the common ingestion → chunking → embedding → indexing → retrieval → generation workflow so you can turn folders, PDFs, repos, databases, or cloud stores into contextualized inputs for an LLM without wiring each step from scratch. The library focuses on simplifying context augmentation (retrieval + prompt synthesis) and offers high‑level APIs to prototype RAG pipelines quickly while supporting production patterns such as persistent vector stores and query engines [^4][^16][^70].

### Key strengths: indexing, retrieval, context augmentation, and connectors
LlamaIndex’s strength is its index-first approach: it provides index data structures and retrieval primitives that make semantic search and document selection precise and efficient. It ships connectors and adapters for many embedding providers and vector DBs (Chroma, Pinecone, Qdrant, Milvus, Weaviate, FAISS, Redis, Postgres/pgvector, etc.), plus reader/parsers for common file types and repo connectors so you can plug your storage backend into the same index/retrieval APIs. The framework also exposes query engines, retrievers, and response‑synthesizer patterns that take retrieved context and produce coherent LLM responses, which helps standardize RAG across backends and LLMs [^28][^29][^30][^70].

### Typical use cases: internal knowledge bases, contract analysis, research assistants, doc search
Typical projects that benefit from LlamaIndex include internal knowledge bases and “search over docs” UX, contract and compliance analysis, research assistants that aggregate and cite source passages, and domain‑specific Q&A (sales playbooks, product docs, SOPs). Because the core abstraction is “index + retriever + query engine,” these use cases translate well: ingest your corpus, build or attach a vector store, and use the query engine / response synthesizer to produce answers grounded in retrieved evidence [^16][^166].

### When to use LlamaIndex vs general orchestration (short decision guidance)
Choose LlamaIndex when your primary challenge is high‑quality document indexing, semantic retrieval, and supplying accurate context to an LLM. If your project centers on indexing many document types, optimizing retrieval strategies, or connecting a specific vector DB, LlamaIndex is purpose‑built for that. If instead you need complex multi‑step orchestration, chaining many external tools, or agentic decision flows where orchestration and tool routing are the focus, a general workflow/agent framework (e.g., LangChain) may be a better fit. The two can also complement each other: use LlamaIndex for retrieval/index quality and a general orchestrator for higher‑level agent logic [^22][^23][^24].

### Teaser: the 5-line claim and what 'ingest & query in ~5 lines' means (tradeoffs)
The “ingest & query in ~5 lines” claim refers to the ability to show a minimal end‑to‑end example that loads files, builds an index, persists it, reloads it, and runs a query in just a few lines of Python. That quick path is great for prototyping and demos, but it hides important tradeoffs: chunking strategy, embedding choices (and their token/costs), retrieval tuning (top_k, filters), and persistence/replication settings. Production systems need explicit control over those knobs and careful handling of embedding costs and vector persistence. Below is a compact 5‑line example using the current core imports (use it to prototype, then expand each step for production):

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, StorageContext, load_index_from_storage  
docs = SimpleDirectoryReader("data/").load_data()  
index = VectorStoreIndex.from_documents(docs, storage_context=StorageContext.from_defaults(persist_dir="./storage"))  
loaded = load_index_from_storage(StorageContext.from_defaults(persist_dir="./storage"))  
print(loaded.as_query_engine().query("Summarize the docs"))

This snippet demonstrates the happy path (ingest → index → persist → load → query). For real applications, explicitly configure chunking, metadata, embedding model, vector‑store choice, and persistence strategy to avoid surprises (e.g., re‑indexing costs or import path/version mismatches) [^58][^70][^166].

## 2. Core concepts and canonical APIs (imports & roles)

### Canonical core imports (examples): from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, StorageContext, load_index_from_storage, Settings
The most commonly used high-level APIs are now exposed from the core namespace. Typical imports in current docs and examples look like:
`from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, StorageContext, load_index_from_storage, Settings`. These core primitives let you load documents, build vector-based indexes, control persistence contexts, and re-load saved indexes (see docs/examples and migration notes) [^82][^112][^166].

### LLM / embedding / vector-store namespaces: e.g. from llama_index.core.llms import LLM; from llama_index.embeddings.huggingface import HuggingFaceEmbedding; llama_index.vector_stores.* adapters
Model backends, embedding implementations, and vector-store adapters live in separate subpackages/namespaces. LLM integrations are often under `llama_index.core.llms` (or provider-specific packages), embeddings under `llama_index.embeddings.*` (e.g., HuggingFace adapter), and vector-store adapters under `llama_index.vector_stores.*` (Chroma, Pinecone, Qdrant, etc.). These are shipped as modular packages so you install just the integrations you need and import from the corresponding adapter namespace [^1][^58][^184].

### Key types & roles: Document/Node, Index (VectorStoreIndex and alternatives), Retriever, ResponseSynthesizer, StorageContext
Documents (and lower-level Node objects) represent ingested content and metadata; an Index (VectorStoreIndex is the primary vector-backed index) stores embeddings and indexes nodes for retrieval. A Retriever is the component that scores/returns relevant nodes for a query, while a ResponseSynthesizer (or query engine wrapper) combines retrieved context with an LLM to produce the final output. StorageContext centralizes persistence pieces (document store, index store, and vector store) and is the object you recreate to load persisted indexes. These roles map to distinct APIs in the core and are the building blocks for RAG pipelines and query engines [^184][^178][^70].

### Common Index APIs and patterns: VectorStoreIndex.from_documents, from_vector_store, as_retriever(), as_query_engine(), persist/load
Common construction and runtime patterns are consistent across examples: load Documents via a reader (SimpleDirectoryReader(...).load_data()), build an index with `VectorStoreIndex.from_documents(...)` (or `VectorStoreIndex.from_vector_store(...)` if you already have a vector backend), derive a retriever or query engine with `index.as_retriever()` / `index.as_query_engine()`, and persist via a StorageContext so you can later `load_index_from_storage(...)`. This pattern supports swapping vector backends (Chroma, Pinecone, Qdrant, etc.) via `StorageContext.from_defaults(vector_store=...)` and avoids re-embedding large corpora [^166][^58][^70]. Minimal example (ingest → index → persist → load → query):
```
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, StorageContext, load_index_from_storage
docs = SimpleDirectoryReader("data").load_data()
index = VectorStoreIndex.from_documents(docs, storage_context=StorageContext.from_defaults(persist_dir="./storage"))
index.storage_context.persist()
loaded = load_index_from_storage(StorageContext.from_defaults(persist_dir="./storage"))
```
After loading, call `loaded.as_query_engine()` or `loaded.as_retriever()` to run queries against the restored index [^166][^184].

### Short reference: function/class signature notes to verify (what to check in API verification)
When verifying APIs in your environment, check the following signature/argument names and behaviors: whether `VectorStoreIndex.from_documents()` accepts `storage_context`, `show_progress`, or `nodes=`; whether `StorageContext.from_defaults()` accepts `persist_dir` or a preconfigured `vector_store` client; whether `load_index_from_storage()` expects a StorageContext instance and an optional `index_id`; and how `as_query_engine()`/`as_retriever()` accept runtime options (top_k, response synthesis params). Because the project was reorganized into a core package plus many modular integrations, also verify the concrete import paths available in your installed llama-index package (ImportError often indicates a version mismatch or missing integration package). If you hit import errors, check `pip show llama-index` / `pip show llama-index-core` and ensure provider-specific packages (e.g., `llama-index-llms-openai`, `llama-index-embeddings-huggingface`, `llama-index-vectorstores-chroma`) are installed as needed; consult the release notes/migration guidance for renames or moved symbols [^76][^82][^100][^88].

References: LlamaIndex docs & examples, run-llama/llama_index GitHub examples, and changelog/migration notes (see cited doc snippets above) [^1][^58][^166][^184].

## 3. Installation, package layout, and choosing integrations

### Recommended pip packages: llama-index (starter), llama-index-core, plus integration packages: llama-index-llms-openai, llama-index-embeddings-huggingface, llama-index-readers-file, vectorstore adapters (pinecone/qdrant/faiss/chroma/redis adapters)
For most quick starts install the main starter package or the modular core plus the provider integrations you need. The common packages you’ll see in docs and examples are:
- llama-index (starter meta-package) or llama-index-core (core API package).
- LLMS integrations: llama-index-llms-openai, llama-index-llms-replicate, llama-index-llms-ollama, etc.
- Embeddings: llama-index-embeddings-huggingface (local Hugging Face embedder) and other provider-specific embedding packages.
- Readers (file loaders): llama-index-readers-file (SimpleDirectoryReader and similar readers).
- Vector store adapters: packages that connect to Pinecone, Qdrant, FAISS, Chroma, Redis, Weaviate, Milvus, Postgres/PGVector, etc.

Install only what you need (e.g., if you’ll use Pinecone + OpenAI, install llama-index-core + llama-index-llms-openai + llama-index-vectorstores-pinecone). The project maintains many small integration packages (hundreds of adapters are available), so avoid installing the entire ecosystem unless you need it [LlamaIndex docs; GitHub]. 

### Modular layout explained: core vs integration packages and why to install only needed adapters
LlamaIndex has been split into a core package that contains the primary APIs (indexes, StorageContext, load helpers, common abstractions) and many small integration packages (LLM drivers, embedding providers, readers, and vector-store adapters). This keeps the core lightweight and reduces dependency bloat. As a result:
- Core APIs and common index classes live under the core namespace (examples: from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, StorageContext, load_index_from_storage).
- Provider-specific code (OpenAI, HuggingFace embeddings, Pinecone, Qdrant, Chroma, Redis adapters) is shipped as separate pip packages and exposes provider modules under the llama_index.* namespaces.

Install only the integrations you plan to use so you avoid extra dependencies and version mismatches; when you see ImportError for an integration symbol, the usual cause is the missing adapter package rather than a bug in the core library [docs & repo examples].

### Versioning & compatibility: pinning strategy and how to find changelog/release notes
Because the project is actively developed and has had import-path reorganizations in past releases, use a stable pinning strategy:
- For production, pin exact versions in requirements.txt (e.g., llama-index-core==0.12.45) or use poetry/poetry.lock / pip-tools (requirements.txt compiled) to lock transitive dependencies.
- For experiments, you can use a looser constraint (e.g., >=X.Y,<X+1) but be ready to update imports if a breaking release occurs.
- Always check the project changelog and GitHub releases/CHANGELOG.md for breaking changes or import-path reorganizations before upgrading a major version. If you see ImportError referencing moved symbols (common after the core refactor), check the release notes and update imports to the new core paths (examples below) [changelog / GitHub].

The five-line logical flow below follows the canonical pattern: ingest, index, persist, reload, query. This uses the core imports above and the StorageContext/load_index_from_storage helpers documented in examples [^82][^166].

```python
# 1) ingest
docs = SimpleDirectoryReader("data").load_data()
# 2) build index (creates vectors & index in-memory or in configured vector store)
index = VectorStoreIndex.from_documents(docs)
# 3) persist (persist_dir uses the built-in storage context; many examples use storage_context.persist)
index.storage_context.persist(persist_dir="indexdir")
# 4) reload from disk/storage
loaded = load_index_from_storage(StorageContext.from_defaults(persist_dir="indexdir"))

retriever = loaded.as_retriever()
print(retriever.retrieve("What is X?"))
```

## 5. Persistence, vector stores, and connector patterns

### StorageContext: patterns for local persist_dir, S3/object store persistence, and custom vector_store in StorageContext.from_defaults()
StorageContext is the canonical storage abstraction in LlamaIndex that groups the document store, index store, and vector store configuration so you can build, persist, and later re-load indexes with the same backing stores. For local persistence the typical pattern is to create or use a StorageContext configured with a persist_dir (or use the from_defaults helper) so indexing writes metadata and vector pointers to disk; later you recreate the same StorageContext and call load_index_from_storage to restore the index without re-embedding everything ([^58][^70]). For object stores you can persist to S3 (or other object stores) by passing the persist target and an fs client when persisting/loading—this lets you store the same on-disk index files in S3 and later rehydrate them by creating a StorageContext that points at the S3 location and providing the same filesystem client ([^58]). If you want direct control of vectors you instantiate a vector_store implementation (e.g., PineconeVectorStore, ChromaVectorStore, or a local FAISS/DocArray implementation) and pass it into StorageContext.from_defaults(vector_store=your_vector_store) so the index uses that backend for vector operations ([^166][^167]). The general rule: persist the index with the exact StorageContext settings (same persist_dir or same vector_store client) to avoid duplicate embedding work when loading later ([^58][^184]).

### Vector store connector list & how-tos: Pinecone, Qdrant, FAISS (local), Chroma, Redis, Milvus, Weaviate, Postgres/PGVector
LlamaIndex ships adapters for a broad set of vector stores so you can pick the store that matches your scale and deployment model: managed cloud stores like Pinecone and Qdrant, open-source/multi-node systems like Milvus and Weaviate, in-process/local stores like FAISS or Chroma, redis-based vector search, and relational options like Postgres with PGVector. The docs and examples enumerate dozens of integrations and show how to construct a specific VectorStore implementation and hand it to StorageContext so VectorStoreIndex operations go through that adapter ([^28][^29][^30]). The right connector depends on your needs: choose FAISS/Chroma for single-machine offline workflows, Qdrant/Milvus/Weaviate for self-hosted production clusters, and Pinecone or managed RedisDB/Cloud DB for managed services. LlamaIndex examples commonly show creating the provider client (or index), wrapping it in the adapter (e.g., PineconeVectorStore(...)), and using StorageContext.from_defaults to bind it to the index lifecycle ([^166][^168]).

### Connector steps per store: install, credentials, create index/collection, upsert vectors, query top_k; mini-benchmark pattern (upsert 1k vectors, measure upsert/query latency)
Connector integration follows a consistent lifecycle across adapters: install the adapter package (or provider client), configure credentials and client options, create or ensure the remote collection/index exists, upsert vectors (typically batched), and run top_k queries for retrieval. In LlamaIndex you normally create the provider client (for example, a Pinecone index object or a Qdrant client), wrap it with the corresponding LlamaIndex VectorStore class, pass that into StorageContext.from_defaults(vector_store=...), and then build or update a VectorStoreIndex via VectorStoreIndex.from_documents(...) so embeddings and upserts are routed through the adapter ([^166][^167][^168]). For a quick performance check, a useful mini-benchmark is: upsert 1k representative vectors (in batches similar to your production batch size), record mean/95th-percentile upsert latency and throughput, then run repeated top_k queries (varying k and concurrency) and measure query latency and QPS. This pattern reveals bottlenecks (network, batching, shard cold-starts) and lets you tune batch size, replica count, or local caching. Always test end-to-end with the same embedding dimensionality and metadata payloads you will use in production, because payload size can affect both upsert and query performance.

### Index lifecycle: incremental updates, reindexing strategies, deduplication transforms, avoiding unnecessary re-embedding
Index lifecycle management is about minimizing rework while keeping the index correct. For incremental updates, prefer upserts to re-creating the full index: insert new documents by embedding and upserting only the new nodes (the vector-store adapters and StorageContext wiring let you do this without rebuilding everything) ([^166]). For schema/transform changes (text-splitting, tokenizer changes), consider partial reindex strategies: compute which documents or chunks changed and re-embed only those, or use a versioned node metadata field so retrievers can ignore old chunks until a background reindex replaces them. Deduplication transforms (hashing content, canonicalizing whitespace, or using lightweight fingerprinting) reduce duplicate embeddings before storage and avoid storage explosion and retrieval noise. To avoid unnecessary re-embedding, store an embedding checksum/version in node metadata so your ingestion pipeline can skip embedding if the content and embedding model/version match a previous run. When a full reindex is unavoidable (major parser change or embedding model change), snapshot the current StorageContext or create a new index_id so you can roll back or compare results without losing the previous index state ([^70][^184]).

### Tips for choosing vector store: scale, metrics (cosine vs ip), latency/cost tradeoffs, local vs managed
Choosing a vector store requires balancing scale, similarity metric semantics, latency and cost, and operational complexity. For similarity metric, understand your store’s default: some stores operate in inner-product (IP) space, others in cosine or L2; cosine similarity can be implemented by normalizing vectors and using IP queries, but behavior differs if you forget to normalize. Latency and cost tradeoffs depend on whether you use a managed remote service (higher per-query cost and network latency but lower ops overhead) versus a local store (lower per-query cost, lower network cost, but requires ops and may need sharding for scale). For very high QPS, prefer a distributed store with replication and GPU/IVF/HNSW tuning (Qdrant, Milvus, Weaviate) or managed services that scale transparently (Pinecone). For experimentation and single-node deployments, FAISS or Chroma work well. Also consider feature needs: metadata filtering, hybrid search (BM25 + vectors), and secure VPC/private network access. Finally, benchmark with realistic data, embedding dims, and concurrency: latency, throughput, and cost per 1M queries are the metrics that will guide a pragmatic choice ([^28][^82][^184]).

## 6. Advanced features & recommended workflows

### Agentic RAG workflows: design a multi-step agent that uses retriever + LLM + tools; example flow & error handling
Design agentic RAG workflows as a sequence of deterministic building blocks: a retriever to fetch context, an LLM to reason and synthesize, and tool integrations (search, database read/write, external API calls) to act. LlamaIndex supports building such multi-step workflows and integrating tools with retrieval (retriever → LLM → tool → retriever loop) so agents can iterate over tasks like research, extraction, or data updates [^1][^3]. A typical flow is: (1) use a lightweight retriever (index.as_retriever()) to fetch top-k candidates; (2) pass retrieved nodes to an LLM prompt or query engine (index.as_query_engine()) for synthesis; (3) if the LLM decides an external tool is required, call the tool and persist results back to the index or a managed data sink; (4) re-run retrieval if more context is needed. To make this robust, implement explicit error handling: timeouts and retry wrappers around tool/LLM calls, a fallback keyword search when semantic retrieval yields low similarity, and guarded output parsing (see next section) to detect malformed or hallucinated responses. For long-running agents, leak-proof the loop with bounded iterations and observability (log each retrieval+tool step) so you can trace decisions and failures [^178][^166].

Example (conceptual) code sketch:
```python
from llama_index.core import VectorStoreIndex
# load or build index...
retriever = index.as_retriever(similarity_top_k=5)
# high-level agent loop:
# 1) retrieve, 2) call LLM/QueryEngine with retrieved nodes, 3) inspect output -> call tool if needed,
# 4) persist results / update index, 5) repeat with guard rails (max_steps, retries).
```
Follow-up behaviors: on retrieval miss, increase top_k or fall back to an inverted-index search (connector-dependent); on tool failure, return a safe error to the user and mark the agent step as retried/aborted in logs.

[^1]: LlamaIndex docs — agents and workflows; [^3]: LlamaIndex tutorials.

### Managed indexes & memory: persisted memory modules, incremental updates, snapshot/restore patterns
Persist indexes and memory to avoid re-creating embeddings and re-ingestion cost. LlamaIndex’s StorageContext is the canonical abstraction for backing stores (document store, index store, and vector store) and is used to persist and later load indexes with load_index_from_storage; you can persist to local disk or object stores like S3 by configuring the StorageContext appropriately [^58][^70]. For managed “memory” (conversation state, short-term facts), use the library’s memory/managed-index modules (docs show managed indexes and memory features) and persist conversational memory to the same storage infrastructure so it survives restarts.

Recommended patterns:
- Incremental updates: append new documents via the index insertion APIs or call VectorStoreIndex.from_documents with a storage_context that points at your persistent vector store; this avoids full re-indexing and preserves vectors already stored [^166].
- Snapshot & restore: periodically snapshot the StorageContext/persist_dir (or the underlying vector DB export). To restore, recreate the same StorageContext (same persist_dir or vector store client) and call load_index_from_storage(storage_context, index_id=...) to reconstruct the index in-process [^58][^70].
- Safety checks: when restoring, validate the vector count and a small sample of retrievals (sanity queries) before re-opening to traffic.

[^58]: StorageContext & load_index_from_storage docs; [^70]: persistence examples (S3, vector stores).

### Transforms & output parsers: deduplication, chunking transforms, output parsers (JSON schema validation)
Use transforms early in the ingestion pipeline to control chunking, deduplicate content, and normalize metadata. LlamaIndex exposes transforms and query-time pipelines so you can apply chunking strategies, deduplication filters, or metadata enrichment to nodes before they enter the vector index (reduces noise and improves retrieval precision) [^1]. On the generation side, use structured output parsers and validators to constrain LLM outputs: define JSON schemas or output-parsers that the LLM must follow, validate the parsed output, and fall back to a second pass or human review if validation fails. This mitigates hallucination and ensures downstream tools receive well-formed data.

Practical tips:
- Chunking: prefer semantic-friendly chunk sizes (e.g.,  500–1,000 tokens per chunk) and keep logical boundaries (paragraphs/sections) where possible.
- Deduplication: run hash-based or fingerprint dedupe on raw text before embedding; additionally, do a vector-similarity dedupe pass during ingestion to avoid near-duplicate nodes.
- Output validation: implement JSON schema validation on structured outputs. If the parser fails, either re-prompt the model with stricter constraints, or escalate to a deterministic extractor (regex or rule-based) for recovery.

[^1]: Transforms & output parser references in docs; [^3]: tutorial notes.

### Observability & evaluation: logging, metrics instrumentation, retrieval quality tests (hit rate), p50/p95 latency measurement and probes
Instrument every layer: ingestion (docs/sec, embed cost), indexing (vectors indexed, errors), retrieval (query QPS, top-k latencies), LLM calls (tokens, response time, errors), and agent/tool steps (success/fail rates). Track retrieval quality via hit-rate tests: maintain a labelled test set of queries with expected documents and compute retrieval hit rate (did the expected doc appear in top-k?). Measure latency SLOs using p50/p95/p99 for both retrieval and generation paths; use synthetic probes to run periodic end-to-end checks (ingest small sample → query → validate response) and alert on regressions.

Implementation pointers:
- Use structured logs and spans (OpenTelemetry / Datadog) around retrieval calls (capture top_k, returned IDs, similarity scores) and around index loads/persists.
- Add metrics: retrieval_hit_rate, retrieval_latency_p50/p95, index_persist_time, embedding_errors, llm_token_usage.
- Run nightly/continuous evaluation suites that exercise domain queries and confirm retrievals and generation quality; fail CI if hit_rate drops below thresholds.

[^178]: Example retrieval instrumentation and callback examples; [^160]: retrieval bug reports illustrating the need for QA.

### Connector-specific patterns for scaling: sharding, hybrid search (sparse + dense), caching strategies
LlamaIndex supports many vector-store connectors (Pinecone, Qdrant, Milvus, Faiss, Chroma, Weaviate, Redis, Postgres/PGVector, Supabase, etc.); choose a backend that matches your scaling, latency, and transactional needs [^28][^29][^30]. For scale, apply standard patterns:

- Sharding / partitioning: partition data by logical namespace/collection (e.g., customer_id, tenant_id, time window) so each vector store index stays smaller and queries hit fewer shards. Use separate vector-store namespaces or multiple indices in the vector DB to isolate workloads; this reduces recall noise and improves latency.
- Hybrid search (sparse + dense): combine sparse retrieval (BM25 / inverted index — Elasticsearch/OpenSearch) to recall candidates, then re-rank by dense embeddings for semantic relevance. Hybrid pipelines reduce false negatives and are especially useful for large corpora where exact-match signals matter.
- Caching: cache top-k answers or retrieval results for frequent queries (with a short TTL) and warm caches on deployment. Cache embeddings for large documents (avoid re-embedding unchanged content). Use consistent caching keys including model version + retriever parameters to avoid stale responses.
- Backend tuning: leverage vector-store features (HNSW, quantization, index replication) and tune index parameters (ef/search_k) to balance recall vs latency. When using managed vector DBs, monitor cost and network egress (embedding persistence can be expensive).

Connector selection and concrete adapter usage is covered in the docs and examples; when changing backends re-create StorageContext with the target vector_store and load or recreate the index via VectorStoreIndex.from_documents / from_vector_store [^166][^58].

[^28]: Supported vector stores list; [^166]: VectorStoreIndex.from_documents & storage_context patterns.

Primary runtime imports for index/persistence are under llama_index.core (e.g., VectorStoreIndex, SimpleDirectoryReader, StorageContext, load_index_from_storage) — update imports if you hit ImportError after upgrades [^82][^88].
- Example persistence pattern: build index → StorageContext.persist(persist_dir=...) → reload with load_index_from_storage(storage_context) [^70][^58].

## 7. Migration, troubleshooting, and best practices

### Notable breaking changes: module reorganization into core + integrations; update imports to llama_index.core when needed
LlamaIndex has been refactored into a small "core" package plus many optional integration packages (LLMs, embeddings, readers, vector stores, etc.). As a result, many symbols that used to be available at the package root have moved under the core namespace or into their integration packages. Concretely, code like `from llama_index import VectorStoreIndex` now should be updated to `from llama_index.core import VectorStoreIndex`; LLM interfaces live under `llama_index.core.llms` and provider-specific adapters live under `llama_index.vector_stores.*`, `llama_index.embeddings.*` or dedicated pip packages (for example, `llama-index-core`, `llama-index-llms-openai`, `llama-index-embeddings-huggingface`) [LlamaIndex docs; GitHub changelog]. If you get an ImportError for a previously available symbol, first try changing imports to the `llama_index.core` path and make sure the corresponding integration package is installed.

### Troubleshooting checklist: pip show llama-index / llama-index-core, confirm virtualenv, check integration package availability, search changelog for symbol moves
When an import or runtime error appears after upgrading, validate the runtime environment and package layout. Confirm which llama-index package is installed and its version with `pip show llama-index` or `pip show llama-index-core` and print the installed version from Python (`python -c "import llama_index; print(llama_index.__version__)"`) to rule out multiple installs or stale system packages. Ensure you are in the intended virtualenv (or container) and that the optional integration packages you rely on (LLM, embeddings, vector-store adapters, readers) are installed; missing integration packages commonly surface as module-not-found errors. If symbols were moved, consult the project's changelog/release notes for the version you upgraded to and search for the symbol name (e.g., `load_index_from_storage`) to find the new import path. A small import test script that simply imports the expected symbols is a quick CI-friendly check:
```python
# import_test.py
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, StorageContext, load_index_from_storage
print("imports OK")
```
Run this from a fresh venv to validate the expected API is available before running larger scripts.

### Common pitfalls and mitigations: index freshness, re-embedding costs, context/LLM token limits, notebook event-loop issues
Indexes drift over time: if your document corpus changes, refresh or incrementally update the index rather than re-building from scratch to avoid repeated embedding costs. Persist indexes or vector collections (via StorageContext / external vector stores) so you can reload without re-embedding; when you must re-embed, batch and cache embedding requests. Token and context limits on your LLM backend constrain how much retrieved context you can synthesize; mitigate this by tuning chunk sizes and retrieval counts, using succinct prompt templates, and post-filtering retrieved nodes to the most relevant ones. Notebook users may run into event-loop conflicts when using async-backed model clients; run LlamaIndex calls in a properly created event loop (or use utilities such as `nest_asyncio` or a small dedicated asyncio loop) to avoid "already running event loop" errors commonly seen in Jupyter environments [LlamaIndex tutorial & examples]. When experimenting, always verify that persistence, retrieval, and query APIs return the expected nodes (metadata and text) before wiring the LLM chain that consumes them.

### Performance & cost tips: chunk size recommendations, top_k defaults, embedding model tradeoffs (dim/latency/cost)
Chunking and retrieval parameters have a direct cost/performance tradeoff: smaller chunks increase retrieval granularity but increase the number of vectors (storage and embedding cost), while larger chunks reduce vectors but can dilute relevance. A practical approach is to choose chunk lengths that keep semantically coherent units (~200–800 tokens) and iterate based on retrieval quality; many teams start around 256–512 tokens and adjust. Lower the number of retrieved documents (top_k) to reduce prompt size and token usage; typical working ranges are 3–10 retrieved items depending on your task and model budget—confirm your LlamaIndex retriever/query-engine default in your installed version and tune it explicitly. Embedding model selection affects dimension, latency, and cost: higher-dimension models (or managed high-quality embeddings) often improve similarity but increase storage and search time; local open-source embedders can be cheaper but slower on CPU. When using vector DBs, enable approximate nearest neighbor and vector compression/quantization features where available to reduce latency and storage cost. Finally, reuse ServiceContext/embedding clients across indexing calls to amortize warm-up/initialization costs [LlamaIndex docs; vector-store integration notes].

### Resources & next steps: authoritative docs, GitHub repo, example notebooks, migration guide, testing & CI checklist (venv validation)
Start with the official LlamaIndex documentation and the GitHub repository to find the canonical import paths, changelog, and migration notes; the docs show the `llama_index.core` import layout and provide example notebooks for ingestion, persistence, and retrieval. Keep a short CI test that creates a fresh virtualenv, installs the minimal set of packages you need (core plus chosen integrations), and runs an import-and-smoke-test script. Example commands to validate in a fresh venv:
```bash
python -m venv .venv && source .venv/bin/activate
pip install --upgrade pip
pip install llama-index-core llama-index-llms-openai  # add integrations you need
python -c "from llama_index.core import VectorStoreIndex, StorageContext, load_index_from_storage; print('OK')"
```
A small 5-line minimal Python example illustrating the common flow (ingest → index → persist → load → query) using the new imports looks like this:
```python
from llama_index.core import SimpleDirectoryReader, VectorStoreIndex, StorageContext, load_index_from_storage
docs = SimpleDirectoryReader("data").load_data()
index = VectorStoreIndex.from_documents(docs)
storage = StorageContext.from_defaults(persist_dir="./storage"); index.storage_context.persist()
loaded = load_index_from_storage(storage)
print(loaded.as_query_engine().query("What is in these documents?"))
```
For CI, add a job that creates a venv, installs pinned package versions, runs the import test above, and executes a small scripted query against a tiny sample corpus to catch import or API regressions early. When migrating production code, pin the exact llama-index-core and integration package versions that you validated and read the project changelog for the target upgrade to capture any symbol moves or removed deprecated APIs [GitHub changelog / release notes; LlamaIndex docs].

If you hit specific errors during migration, collect the installed package versions (`pip show`), the failing import traceback, and the simple import test above; these artifacts make it easy to map the problem to a known breaking change or a missing integration package when filing an issue or searching the changelog.
